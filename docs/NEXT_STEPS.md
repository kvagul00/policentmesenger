# Следующий этап

Приоритет пользователя: рабочий мессенджер сейчас, импорт базы позже.

## 1. Общая история и сотрудники

Определить среду размещения backend и PostgreSQL. Создать миграции:
users, channels, channel_members, messages, message_attachments, message_reactions, orders, order_assignments, order_stage_events, payment_events, audit_events.

Вход сотрудников и роли назначаются на сервере. Не доверять автору сообщения, роли, membership и статусам, пришедшим от клиента. Оплата — manager, этап — назначенный исполнитель или менеджер. Заказы и статус оплаты доступны сотрудникам по согласованным правилам.

## 2. Сообщения

API с пагинацией и стабильными ID; история в PostgreSQL, idempotency key при отправке. WebSocket или SSE с восстановлением по event_id, проверка членства в канале. Два компьютера должны видеть одно новое сообщение и сохранять его после перезагрузки.

## 3. Вложения и эксплуатация

Объектное хранилище, авторизованная загрузка/скачивание, квоты, резервные копии. Ограничения localStorage больше не использовать как хранилище рабочих файлов. Логи без персональных данных и содержимого сообщений.

## 4. Перенос интерфейса

Сохранить проверенные сценарии прототипа. Разделить слой API/хранилища и представление. Отдельно решить, требуется ли перенос существующей демо-переписки пользователя: автоматически в Git её не загружать.

## 5. Интеграции позже

Access/Excel/CSV → адаптер → неизменяемый снимок → staging → проверки → подтверждённая публикация заказов. UUID заказов сохраняют связь с чатами. Импорт не перезаписывает сообщения, ручные этапы и подтверждённую оплату.

## Критерии рабочей версии

- Два сотрудника на разных ПК обмениваются сообщениями.
- История общая и сохраняется после повторного входа.
- Права проверяются API, недоступные действия отклоняются сервером.
- Вложения доступны только разрешённым участникам.
- Смена этапа и подтверждение оплаты имеют аудиторский след.
- Не требуется включённый компьютер разработчика.
